## 2. 追加修正（第4版）

### 2-1. 30fps制限と性能不足の判別（D2 で実装）

**原則：OS による30fps制限（iOS の低電力モードなど）と GPU 性能不足は、フレーム時間だけでは区別できない。
確実な根拠がない限り、どちらとも断定しない。**

1. **確実に判別できる情報がある場合だけ自動判定する**
   - GPU の処理時間を計測できる拡張機能（`EXT_disjoint_timer_query_webgl2`）が使える環境では、
     「CPU の処理時間 + GPU の処理時間」がフレーム予算より十分小さい（予算の50%未満が続く）のに
     フレーム間隔が約33.3msで一定、という場合に限り「外部要因による上限」と判定し、画質を下げない。
   - この拡張機能は iOS Safari や多くの Android では使えない。その場合は判別できないものとして 2〜5 に従う。
2. **判別できない場合は、通常どおり画質の段階を1つずつ下げる**（OS 制限と断定して調整を止めることはしない）。
3. **「下げても改善しない」ことを検出する**
   - 段階を下げるたびに、変更前後のフレーム時間（p90）を記録する。
   - 2段階続けて下げても p90 の改善が 5% 未満なら「画質を下げても速くならない状態」とみなし、
     それ以上は下げずに、効果のなかった2段階を元に戻す。
     （OS の上限、CPU が限界、ブラウザの制限など。原因は断定しない）
4. **最低画質でも性能不足が続く場合、または 3 に該当した場合は、30fpsモードへの切り替えを提案する**
   - 自動で切り替えず、画面に控えめな案内を出す：「動作が重いようです。30fpsモードに切り替えますか？［切り替える］［このまま］」
   - 「このまま」を選んだ場合、そのセッション中は同じ案内を再表示しない。
5. **30fpsモードは手動でも選べる**（開発パネル → 将来の設定画面）。選択は端末に保存する。
6. **無限ループを起こさない仕組み**
   - 段階は 0〜9 の有限の範囲で、9 より下には下げない。段階9に達したら自動の引き下げを止める。
   - 引き上げにはお試し期間を設け、失敗した段階への再挑戦は禁止時間を倍々に延ばす（60秒 → 120秒 → …、上限10分）。
   - 30fps と 60fps の自動での往復はしない。60fpsへ戻すのは手動か次回起動時のみ。
   - 30fpsモード中も同じ規則で判定する（予算 33.3ms）。段階9でも足りなければ、案内を1回だけ表示して調整を止める。

### 2-2. 基本移動（待機・歩行・走行）のブレンド計算（C1〜C2 で実装）

**混ぜ合わせの変数**：キャラクターの実際の水平速度 `v`（入力値ではなく、CharacterController が計算した速度。急な変化を避けるため 0.1 秒程度でならす）。

**重み（合計は常に 1）**

| 区間 | 待機 | 歩行 | 走行 |
|---|---|---|---|
| `v ≤ 0.05` | 1 | 0 | 0 |
| `0.05 < v < V_walk` | `1 − t` | `t`（`t = v / V_walk`） | 0 |
| `V_walk ≤ v < V_run` | 0 | `1 − t` | `t`（`t = (v − V_walk) / (V_run − V_walk)`） |
| `v ≥ V_run` | 0 | 0 | 1 |

- 同時に0より大きい重みを持つのは最大2つ。計算後に合計で割って正規化し、浮動小数点の誤差を除く。
- `V_walk = 3.5 m/s`、`V_run = 7.0 m/s`（初期値。データで調整可能）。

**速度・歩幅・周期の関係**

- 1周期 = 左右1歩ずつ（2歩）。クリップは「左足の接地 = 位相0」「右足の接地 = 位相0.5」で揃えて作る。
- `D` = 1周期で進む距離（= 歩幅 × 2）。体型プロファイルの脚の長さに比例させる：`D = D_A × (脚の長さ / 体型Aの脚の長さ)`。
- 初期値（体型A）：歩行 `D_walk = 2.0 m`（歩幅1.0m）、走行 `D_run = 3.2 m`（歩幅1.6m）。
- **位相の進み方**：`dφ/dt = v / D_blend`。`D_blend` は歩行と走行の重みで線形に混ぜた周期距離。
  - 歩行と走行は同じ位相 `φ` で読み出すので、混ぜても足の運びがずれない。
  - 待機は位相を共有せず、独自の時間で再生する。
- 結果として、周期の長さ `T = D / v`、1秒あたりの歩数 `= 2v / D`：
  - 歩行 3.5 m/s：T ≈ 0.57秒、約3.5歩/秒（早歩き〜小走りの見た目）
  - 走行 7.0 m/s：T ≈ 0.46秒、約4.4歩/秒（全力に近い走り）

**足の滑りの確認（チェックポイントC）**

- 自動計測：接地している足（接地区間はクリップのイベントで定義）のワールド座標の水平方向のずれを、接地区間ごとに計測し、**2cm 以内**を目標とする。
- 目視：歩行・走行・その中間の速度で、足元を横から映したスクリーンショットの連続画像で確認する。
- 調整の手段：`D_walk` / `D_run`、各クリップの接地区間、`V_walk` / `V_run`。いずれもデータの変更だけで調整できる。
- 注意：歩行 3.5 m/s は人間の歩行としては速いため、見た目が小走りに近くなる。チェックポイントCで実際の見た目を確認し、必要なら速度の初期値の変更を提案する。

## 4. A1 監査後の整理（範囲の確定）

### 4-1. A1 に残した基盤機能と、その位置づけ

| 機能 | 位置づけ |
|---|---|
| 固定60Hzのティック分割（`FixedStepAccumulator`） | 基盤。ティック間の描画補間（alpha）は **B2 で実装**する。A1 では計算もしない（未使用の値を捨てる処理は削除済み）。端数時間 `accumulator` を保持する構造は B2 で再利用する |
| 30fps上限の手動設定（`FrameLimiter`） | 手動の画質切り替えの一部 |
| 画面サイズ・リサイズ・回転・ピクセル倍率の変化への対応（`ViewportManager`） | 描画解像度を正しく保つための基盤。安全領域に合わせたUI配置・「横向き推奨」表示は **B1** |
| タブ非表示時のゲームループ停止 | 基盤 |
| WebGLコンテキストの喪失・復帰への対応 | 基盤（4-3） |
| OrbitControls による視点操作 | **仮シーン（`src/debug/TestScene.ts`）専用のデバッグ機能**。B1〜B3 の入力システム（InputCommand・PointerRouter・Pointer Lock）の先行実装ではない。**A2 で仮シーンをアリーナに置き換えるときに、仮シーンごと削除する** |

`user-scalable=no` はアクセシビリティ上の問題があるため削除した（`viewport-fit=cover` は維持）。
ゲーム画面（canvas）上のピンチ・ダブルタップ拡大は `touch-action: none` で止まり、開発パネルなど canvas 以外の要素は通常どおり拡大・スクロールできる。

### 4-2. D2 に延期した機能（設計のみ記録）

1. **画質設定の保存と読み込み**
   - 保存するもの：画質の段階、フレームレートモード（60 / 30）、30fpsモードの提案を「このまま」で断ったかどうか（セッション単位）。
   - 保存先：`localStorage`。読み書きはすべて例外を握りつぶす薄いラッパー経由にする（プライベートブラウズ・保存の無効化でもゲームは動き続ける）。
     将来のアプリ化ではこのラッパーをネイティブの保存機能に差し替える（`PlatformServices`）。
   - 優先順位：URLパラメータ ＞ 保存した値 ＞ 初期値の推定。
   - 自動調整で下げた段階を保存するのは、その段階で安定して動作した場合（一定時間、下げる条件を満たさなかった場合）だけにする。
2. **端末に応じた初期画質の推定**
   - 手がかり：主な入力が指か（`(pointer: coarse)`）、画面の物理解像度、GPU の名前（`WEBGL_debug_renderer_info` が使える場合のみ）。
   - 推定はあくまで開始点で、実際の段階は自動調整（2-1）で決まる。推定だけで最低画質から始めることはしない（指で操作する端末でも「中」から始める）。

A1 では、初期画質を固定値 **段階3（中）・60fps** とする（`DEFAULT_QUALITY_LEVEL`）。URLパラメータで変更できる。

### 4-3. WebGLコンテキストの喪失・復帰と GPU 資源の管理

- 問題：復帰後に、喪失前に作られた影マップ・RenderTarget などを dispose すると、
  three.js の古い管理情報が古いコンテキストの GL オブジェクトを削除しようとして
  `INVALID_OPERATION: delete: object does not belong to this context` が発生していた。
- 対策：**コンテキストを失った時点**（GL の呼び出しが何もしない状態）で、把握しているすべての GPU 資源を dispose する
  （EffectComposer のバッファ、各パスの作業バッファとマテリアル、シーン内のジオメトリ・マテリアル・テクスチャ・影マップ）。
  three.js の資源は dispose 後も再利用でき、復帰後の最初の描画で新しいコンテキストに作り直される。
- 規則（A2 以降も守る）：**シーンに含まれない GPU 資源**（非表示のプール、キャッシュ、ステージの切り替え用に保持しているものなど）を持つシステムは、
  コンテキスト喪失時に同様に解放する仕組みを持つこと。
- 復帰後は描画バッファの組み合わせを再検証する（4-4）。

### 4-4. HDR / MSAA の描画バッファのフォールバック

- 試す順番：HDR + MSAA → HDR（MSAAなし）→ 8bit + MSAA → 8bit（MSAAなし）→ すべて失敗したらエラーを表示して停止。
  （RGBA8 の MSAA は WebGL2 の必須機能なので、8bit で MSAA を再び試す）
- 検出方法：バッファの組み合わせを変えた直後の描画（初回描画を含む）で、
  ① 各 RenderTarget のフレームバッファの完全性（`checkFramebufferStatus`、MSAA 用と解決先の両方）、
  ② GL エラー（`getError`。検証するフレームだけ確認する）を調べる。
- 一度失敗した組み合わせは記録し、画質を切り替えても再び試さない。
- Bloom の作業バッファも同じ種類（HDR / 8bit）に合わせる。8bit では Bloom のしきい値を 1.0 から 0.8 に下げる
  （8bit では各色が 1.0 で切り詰められ、強い発光でも輝度が 1.0 未満になるため。例：#ffb347 ×4 → 輝度 約0.945）。
- 統計表示には「実際に使っている MSAA（要求された値）」「HDR / 8bit」「失敗した組み合わせ」を表示する。

### 4-5. three.js の内部実装への依存（A1 最終監査で整理）

フレームバッファの完全性の事前検査だけが three.js の内部実装に依存する。依存は `src/render/internal/threeRenderTargetProbe.ts` の1ファイルに隔離した。

| 依存先 | 内容 | 確認したバージョン |
|---|---|---|
| `renderer.properties`（公開プロパティだが中身は内部の管理情報） | `properties.has / get(renderTarget)` | three.js 0.187.0（REVISION '187'） |
| `__webglFramebuffer` | 解決先（MSAAなしの場合は描画先）のフレームバッファ | 同上（`WebGLTextures.js` の `setupRenderTarget`） |
| `__webglMultisampledFramebuffer` | MSAA 用のフレームバッファ（samples > 0） | 同上 |

- **内部 API を使う理由**：公開 API の `renderer.setRenderTarget()` でバインドされるのは MSAA 用の側だけで、
  解決先（HDR テクスチャ側）を描画前に検査する公開 API が無いため。
- **公開 API で済ませている部分**：バッファの確保（`renderer.initRenderTarget`）、描画後の GL エラー検査（`gl.getError`）。
- **three.js の状態キャッシュとの関係**：
  - three.js の `WebGLState.bindFramebuffer` は `FRAMEBUFFER` / `DRAW_FRAMEBUFFER` / `READ_FRAMEBUFFER` ごとにバインド状態をキャッシュする
    （`FRAMEBUFFER` と `DRAW_FRAMEBUFFER` は同一として扱い、`READ_FRAMEBUFFER` は別に管理）。
  - 検査では `DRAW_FRAMEBUFFER` / `FRAMEBUFFER` には一切触れず、`READ_FRAMEBUFFER` だけにバインドして
    `checkFramebufferStatus(READ_FRAMEBUFFER)` で調べ、終了後に `READ_FRAMEBUFFER` を検査前の値へ正確に戻す。
    これにより、実際のバインド状態と three.js のキャッシュの関係は検査の前後で変わらない。
  - three.js は `READ_FRAMEBUFFER` を使う直前（MSAA の解決など）に必ず自分でバインドし、使用後に null に戻す。
- **修正前の実装との違い**：修正前は `FRAMEBUFFER` に直接バインドして検査し、検査前の `FRAMEBUFFER`（= DRAW）の値で戻していた。
  現在の呼び出し位置（`initRenderTarget` の直後で、どちらも null）では結果的に正しかったが、
  検査中に DRAW 側がキャッシュと食い違うことと、READ 側を元の値ではなく DRAW の値に戻すことが潜在的な弱点だった。
- **将来の three.js 更新時の注意**：
  - 上記の内部プロパティ名が変わっていないか確認すること（`VERIFIED_THREE_REVISION` を更新する）。
  - 内部プロパティが見つからない場合、事前検査は「判定不能」を返し、描画後の GL エラー検査だけで判定する
    （コンソールに1回だけ注意を出す）。判定不能を「成功」とはみなさない。
